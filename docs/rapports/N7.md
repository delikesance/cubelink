# N7 : protocole d'ajout d'ami (`p2p/src/friend_proto.rs`)
- ALPN `cubelink/friend/1`, un flux bidi par demande, trames u32 BE (4 Kio max), délais par message, signatures ed25519 sur `domaine | corps`, vérifiées avant tout effet de bord.
- Ordre : REQUEST(H(pk|nonce_A)) -> COMMIT(H(pk|nonce_B), écho) -> REVEAL A -> REVEAL B (après vérification de l'engagement de A) -> code `verify_code` des deux côtés -> DECISION signée de B (le flux reste ouvert).
- B range la demande (`upsert_request`, `In`) seulement une fois le code calculé (la base exige un code valide), puis émet `IncomingRequest`. Ami créé dans `accept` (B) et à la réception d'une acceptation valide (A, événement `Accepted`). `Refused` sinon. A ne range rien dans la base pour sa demande sortante.
- API : `FriendService::start/start_with_config/attach` (+ `handler()` si un `Router` existe déjà), `set_name`, `send_request(code) -> VerifyCode`, `accept(pk) -> Friend`, `refuse(pk)`, `FriendEvent`, `FriendConfig`.
- Défenses : horodatage ±5 min, engagement jamais rejouable (cache), message destiné à un tiers, identité de transport = clé du message, un état par pair, plafonds (total en cours, par pair/heure, demandes stockées, poignées de main simultanées) avec rejet silencieux.
- Tests (11 verts, 2 endpoints iroh locaux, relais désactivé) : échange complet + acceptation, refus, signature falsifiée, surdimensionné, rejeu/ancien/tiers, nonce != engagement (des deux côtés), MITM (codes différents), soi-même, anti-spam. Clippy `-D warnings` propre.
- Limite `Identity` : pas d'accès à la clé secrète ; l'endpoint iroh doit être créé avec la même clé (les tests relisent `identity.key`). Le pair est vérifié via `conn.remote_id() == clé du message` : l'app doit donc construire l'endpoint depuis l'identité (demander `Identity::secret_bytes()` au team lead).
- Risque : 64 bits de code restent grindables hors ligne, mais l'engagement empêche d'ajuster la clé après avoir vu les nonces.
