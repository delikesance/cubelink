# N1 : spike Iroh (tunnel QUIC, transfert par hash, relais)

Date : 2026-11-09. Code : `spike/p2p-tunnel/` (crate autonome, `src/main.rs`).
Machine : Windows 11, une seule machine, tout en boucle locale / LAN domestique. Build release.

## 1. Versions

| Crate | Version | Remarque |
|---|---|---|
| iroh | **1.4.1** (`=1.4.1`) | dernière sur crates.io (`cargo search`) ; MSRV 1.91 ; toolchain utilisée : cargo 1.99 |
| iroh-blobs | **0.104.1** (`=0.104.1`) | dernière ; dépend de `iroh ^1.0.0`, `iroh-base ^1.0.0` : compatible avec iroh 1.4.1 (un seul `iroh` dans `cargo tree`) |

- iroh 1.x est une API stable (semver 1.0) ; la compatibilité d'iroh-blobs est assurée par la contrainte `iroh = "1.0.0"`.
- **Mise en garde officielle** (README d'iroh-blobs 0.104) : « not yet considered production quality. For now, if you need production quality, use iroh-blobs 0.35 ». Or 0.35 dépend d'iroh 0.35 (pré-1.0), incompatible avec iroh 1.x. C'est le principal risque (voir §6).
- L'API a beaucoup changé par rapport aux exemples de 2024-2025 : `NodeId` devient `EndpointId`, `NodeAddr` devient `EndpointAddr`, presets (`presets::N0`, `Minimal`), `Endpoint::paths()` pour inspecter direct/relais. Les exemples de iroh-blobs 0.104 (`examples/transfer.rs`) sont à jour.
- Dépendances de la feature `test-utils` d'iroh activée uniquement pour lancer un relais local en test ; elle n'est pas nécessaire en production.

## 2. Ce qui fonctionne (vérifié par exécution)

Commandes (dans `spike/p2p-tunnel`, avec `CARGO_TARGET_DIR` défini) :
`cargo run --release -- <direct|relay|n0> <tunnel|blobs|resume|all> [taille_Mo]`
(`RELAY_ONLY=1` avec `n0` désactive l'IP : relais public uniquement.) Aucun test automatisé (`cargo test`) n'a été écrit : les vérifications sont des `ensure!` dans le binaire.

1. **Connexion par clé publique** : le nœud B se connecte à A uniquement via `EndpointAddr` (id + adresses de transport). Fonctionne dans les trois modes.
2. **Tunnel** : flux QUIC bidirectionnel <-> serveur TCP echo local (B écoute TCP en local, chaque connexion TCP = un flux bidi QUIC vers A, A relie à l'echo). Écho correct, 100 Mo aller + 100 Mo retour sans erreur.
3. **Transfert par hash (iroh-blobs)** : fichier aléatoire de 50 Mo, import dans un `FsStore` (A), fetch par B avec `store.remote().fetch(conn, HashAndFormat)`, export, **hash BLAKE3 recalculé identique** et comparaison octet à octet identique. Hash inconnu côté A : le fetch échoue proprement (`stream reset by peer`).
4. **Coupure puis reprise** : connexion QUIC fermée à ~20 Mo (40 %) -> erreur `connection lost` ; fermeture puis réouverture du store sur disque (simule un redémarrage) -> 20 Mo présents localement (`remote().local()`), puis fetch qui ne télécharge que **30 Mo** (payload lu = 30 Mo sur 50). La reprise fonctionne au niveau octets (vérification BAO incrémentale), et le résultat final est vérifié (hash identique).

## 3. Mesures (une seule machine)

Toutes les mesures sont locales. Elles mesurent le coût logiciel d'Iroh (QUIC + chiffrement + TCP local), pas un réseau réel.

| Scénario | Connexion | RTT tunnel 64 o (n=2000) | Débit tunnel (100 Mo dans chaque sens) | Blob 50 Mo | Reprise (30 Mo restants) |
|---|---|---|---|---|---|
| `direct` (relais désactivé, IP locales) | établie en 2,5 ms | p50 211 µs, p95 281 µs, p99 343 µs, max 579 µs | 92 Mo/s par sens (774 Mbit/s) en 1,08 s | 0,27 s = 189 Mo/s (1,5 Gbit/s) | 0,15 s |
| `relay` (relais iroh-relay **local** sur 127.0.0.1, IP désactivé) | 11 ms | p50 308 µs, p95 388 µs, p99 447 µs | 36 Mo/s par sens (303 Mbit/s) en 2,77 s | 1,45 s = 34 Mo/s (275 Mbit/s) | 0,86 s |
| `n0` (presets N0 : relais publics n0 + IP) | 10 ms ; chemin choisi : **IP directe** (IPv6 LAN) | p50 214 µs | 105 Mo/s par sens (881 Mbit/s) | 0,24 s pour la reprise de 30 Mo | OK |
| `n0` + `RELAY_ONLY` (relais public n0 `euc1-1.relay.n0.iroh.link`, via Internet) | 204 ms | **p50 67 ms**, p95 80 ms, p99 118 ms, **max 5,9 s** (un pic) | **1,0 Mo/s** par sens (8 Mbit/s) ; 100 Mo en 103 s | 10 Mo en 7,9 s = 1,3 Mo/s (hash vérifié) ; le run 50 Mo à la suite du test tunnel n'a pas produit de résultat (voir §4) | non mesuré |

Autres chiffres : hash BLAKE3 + import de 50 Mo ~ 75-93 ms sur SSD. Surcoût du protocole : 50 Mo de payload = 52,63 Mo lus au total (+0,4 %, arbre BAO).

Lecture :
- Le tunnel local ajoute environ 0,2 ms de RTT et n'est pas un goulot pour Minecraft (jeu = 50-200 kbit/s par joueur selon `architecture.md`).
- Le débit via relais est ~1 Mo/s sur le relais public n0 depuis ma connexion : cela confirme que **les relais publics ne conviennent pas au transfert de mods** (cf. règle de `architecture.md` §3 : gros fichiers en direct uniquement, ou débit plafonné). Ce chiffre dépend de mon lien Internet et d'un relais précis (Francfort) ; ce n'est pas une garantie.
- Le relais local (36 Mo/s) montre seulement que le code du relais n'est pas lent en soi ; il ne prédit pas un relais auto-hébergé sur VPS.

## 4. Ce qui ne peut PAS être mesuré ici, et échecs

- **Taux de hole punching réel entre deux réseaux : NON MESURÉ.** Les deux nœuds sont sur la même machine / le même LAN, donc le chemin direct est trivial (aucun NAT traversé). L'affirmation de `architecture.md` (« hole punching échoue dans ~10-20 % des cas ») n'est ni confirmée ni infirmée par ce spike. Il faut un test à deux réseaux distincts (par ex. un ami en 4G/box différente), avec plusieurs types de NAT, en lisant `conn.paths()` (IP vs RELAY, déjà journalisé par le spike) et le temps avant bascule en direct.
- Latence/débit WAN réels entre amis : non mesurés (seul le relais public n0 a été touché via Internet).
- Comportement sous NAT symétrique, CGNAT, réseaux d'entreprise : non testé.
- **Échec/anomalie** : le run `RELAY_ONLY=1 n0 all 50` (tunnel 100 Mo puis blob 50 Mo, via relais public) n'a rien affiché après l'import du blob (sortie coupée, probablement le timeout de 300 s de ma commande après les 103 s du tunnel, mais je ne l'ai pas confirmé). Le même test avec 10 Mo passe. Cause non investiguée : à retester avant de conclure sur la tenue du relais public aux gros transferts.
- Le test « blob 50 Mo » en mode `n0` (chemin IP) a été vérifié à 20 Mo coupés + 30 Mo repris ; le run complet sans coupure 50 Mo est vérifié en `direct` et `relay` local.
- 1re connexion avec `ep.online()` non attendu en `direct` (les adresses IP locales sont déjà dans `addr()`).

## 5. Configuration du relais, « relais seul » / « direct seul »

Tout cela a été **validé par exécution** (modes `direct` et `relay` ci-dessus).

- **Relais publics n0** : `Endpoint::builder(presets::N0)` (relais prod + découverte DNS/pkarr n0). Best effort, pas de SLA, débit limité (cf. 1 Mo/s mesuré).
- **Relais auto-hébergé (iroh-relay)** : `RelayMode::Custom(RelayMap::from_iter([relay_url]))` (ou `RelayMode::custom(urls)`), avec `presets::Minimal` pour ne pas utiliser le DNS de n0. Le binaire serveur `iroh-relay` (crate du même nom, feature `server`) tourne sur un VPS avec TLS (Let's Encrypt via la config du serveur, ou certificats manuels) ; `iroh::test_utils::run_relay_server()` l'a lancé en test (certificat auto-signé, d'où `ca_tls_config(CaTlsConfig::insecure_skip_verify())` côté client, à ne jamais faire en production). Non testé : déploiement réel sur VPS, TLS Let's Encrypt, contrôle d'accès (`AccessControl`).
- **Direct uniquement** : `RelayMode::Disabled` (aucun relais, ni écoute ni connexion) ; équivalent plus fin : `clear_relay_transports()`. L'adresse à donner à B doit alors contenir des IP joignables (`ep.addr()` les fournit), ou être obtenue par une découverte (mDNS, pkarr/DNS). Si le chemin direct est impossible, la connexion échoue : c'est le comportement voulu pour « direct only ».
- **Relais uniquement** : `clear_ip_transports()` côté endpoint (aucun socket UDP direct) et fournir une adresse ne contenant que le relais. Mesuré en local et via le relais public.
- **Sélection de chemin par connexion** : `conn.paths()` / `paths_stream()` indiquent chaque chemin (`is_ip()`, `is_relay()`, `is_selected()`, `rtt()`), ce qui permet d'afficher « connexion directe / via relais » et de couper un transfert de mods si le chemin sélectionné est un relais (N17). Un `PathSelector` personnalisé existe mais est derrière la feature instable `unstable-custom-transports` : ne pas s'y appuyer.
- Découverte : en mode N0, `ep.addr()` publie relais + IP ; en `Minimal`, pas de découverte : l'adresse doit être transmise (ticket) ou fournie par une `MemoryLookup`/mDNS.

## 6. Limites et risques

1. **iroh-blobs 0.104 : explicitement « pas production quality »** (README). Aucun bug rencontré pendant le spike (hash, export, reprise, hash inconnu OK), mais l'API a changé de nom plusieurs fois et peut encore changer. Mitigation : isoler iroh-blobs derrière `p2p/src/transfer/*`, épingler `=0.104.x`, ou n'utiliser qu'Iroh (QUIC) + un protocole de transfert maison (le hash BLAKE3 reste possible via le crate `blake3`).
2. **Hash : BLAKE3** (natif iroh-blobs). Ça tranche en partie le point ouvert de `architecture.md` §7 : si on utilise iroh-blobs, la clé de contenu est BLAKE3 ; garder SHA-256/SHA-1 du manifeste Modrinth pour la vérification de provenance, et mapper vers BLAKE3 dans le cache local.
3. **Le taux de hole punching réel est inconnu** : le dimensionnement du relais (§3 « Trajectoire de coût » de `architecture.md`) repose sur ~10-20 % d'échec non vérifié.
4. **Relais publics n0** : débit ~1 Mo/s mesuré, pas de SLA. Suffisant pour du trafic de jeu, pas pour des mods. Prévoir tôt le relais auto-hébergé et le « direct uniquement » pour les transferts.
5. **Taille de dépendances** : 476 paquets au lock, compilation initiale longue (plusieurs minutes) ; binaire non mesuré.
6. **Ressources** : `iroh-blobs` utilise `redb` pour le store fs ; le chemin du store doit être unique par processus (un seul propriétaire).
7. **Identité Minecraft** non prouvée par Iroh (déjà noté dans l'architecture) : la clé publique prouve l'identité du pair Iroh, pas du joueur Mojang.

## 7. Invité hors ligne et monde LAN Minecraft : NON VÉRIFIÉ

Je n'ai pas lancé Minecraft. Ce spike ne teste **ni** l'ouverture d'un monde en LAN, **ni** la connexion d'un client Minecraft vers le port du tunnel, **ni** le cas d'un invité en mode hors ligne (sans compte Microsoft valide / `online-mode=false`). Points à vérifier plus tard : (a) un monde « ouvert au LAN » écoute sur un port aléatoire annoncé en multicast : l'hôte doit le lire (log ou paquet LAN) pour le passer au tunnel ; (b) le serveur intégré LAN est en `online-mode=true` : un invité sans session Mojang valide sera refusé, sauf autorisation spécifique ; ce comportement dépend de la version et n'est pas validé. Le tunnel TCP lui-même (flux QUIC <-> TCP) est validé techniquement avec un faux serveur echo, ce qui suffit pour N14.

## 8. Décision recommandée : **GO conditionnel pour Iroh** (contre libp2p)

Justification :
- Ce qui est validé : connexion par clé publique, tunnel QUIC <-> TCP à faible surcoût (~0,2 ms), transfert par hash vérifié, reprise sur coupure à l'octet près, contrôle explicite direct/relais, relais auto-hébergeable (testé en local). Tout cela avec peu de code (un binaire de ~450 lignes) et une API de haut niveau.
- libp2p (rust-libp2p) offre le même socle (QUIC, DCUtR pour le hole punching, relay v2) mais impose d'assembler soi-même identité, découverte, relais, protocole de transfert et vérification : plus de code et plus de configuration. Je n'ai **pas** testé libp2p dans ce spike : la comparaison est fondée sur l'effort, pas sur une mesure.
- Conditions du GO (à lever avant la phase 3 « vrai produit ») :
  1. Test à **deux réseaux réellement distincts** pour mesurer le taux de connexion directe (bloquant pour dimensionner le relais).
  2. Décider si on dépend d'iroh-blobs 0.104 (non « production quality ») ou si on isole la couche de transfert pour pouvoir la remplacer (recommandé : trait `Transfer` dans `p2p/src/transfer/`).
  3. Relais : commencer avec les relais publics n0 pour la présence/jeu uniquement ; transferts de mods en **direct uniquement** ; déployer un `iroh-relay` auto-hébergé avant toute ouverture publique.
  4. Retester le transfert de 50 Mo via relais public (anomalie §4).
- Condition de NO-GO / bascule vers libp2p : si le test à deux réseaux montre un taux d'échec direct très supérieur à 20 % **et** que le relais auto-hébergé ne suffit pas, ou si iroh-blobs 0.10x s'avère instable pour le transfert de gros jeux de fichiers.
