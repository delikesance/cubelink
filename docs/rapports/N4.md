# N4 : code de vérification (`p2p/src/verify_code.rs`)
- `verify_code(my_pub, their_pub, nonce_a, nonce_b)` : SHA-256 de `cubelink/verify/v1` puis des paires (clé, nonce) triées par clé, champs préfixés par leur longueur (u32 BE). 8 premiers octets conservés.
- `nonce_a` accompagne `my_pub`, `nonce_b` accompagne `their_pub` : résultat identique des deux côtés.
- `format_code` -> « 3F9A · C21B · 77D0 · 5E14 » ; `parse_code` tolère espaces, tirets, « · », minuscules ; `codes_match` en temps constant.
- `CODE_BITS = 64` : suffit contre un MITM opportuniste, pas contre un attaquant qui grinde des clés hors ligne pendant des jours.
- **Exigence pour N7 (non implémentée ici)** : lier le code à des engagements. Chaque pair envoie d'abord `H(nonce)` (commit), ne révèle son nonce qu'après avoir reçu l'engagement de l'autre, et le code n'est calculé qu'après vérification des révélations. Sans cela, un MITM peut grinder sa clé pour coller au code après avoir vu les nonces.
- Tests : proptest (symétrie, déterminisme, aller-retour), MITM simulé, nonces, format, parse, 10 000 tirages sans collision.
